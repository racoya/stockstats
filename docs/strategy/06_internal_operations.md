# Internal Operations: The Trading Desk Dashboard

## 1. Objective
To define the proprietary user interface (UI) and backend access controls that our team will use to monitor, manage, and override the automated trading system. This is our bespoke internal Bloomberg Terminal.

## 2. User Roles & Permissions Architecture
Because this is proprietary capital, access must be strictly compartmentalized.

*   **Admin (Founders/Quants):** Full read/write access. Can deploy new algorithms, edit raw codebase logic, adjust global risk limits, and trigger global kill switches.
*   **Senior Trader (Execution/Monitoring):** Read/write access within bounds. Can manually enter/exit trades, adjust strategy parameters within predefined limits (e.g., tweaking the take-profit target slightly), and monitor all active positions. Cannot alter the core logic codebase or exceed hard risk limits.
*   **Analyst (Research):** Read-only access. Can view historical data, backtesting results, and live performance dashboards to identify new statistical edges or investigate execution slippage, but cannot execute trades.

## 3. Trader Tracking & The Immutable Ledger
We must solve the "Who did this?" problem that happens when algorithms and humans interact in the same account.

*   **The Audit Log:** Every single order (whether generated by Algo A, Algo B, or manually clicked by a Trader) must be appended to an immutable database ledger.
*   **Tagging:** 
    *   `Source_ID`: 'Algo_MeanRev_BTC' or 'Trader_JohnDoe'
    *   `Timestamp_UTC`
    *   `Authorization_Level`
*   **Trader-Specific PnL:** The dashboard must calculate and display the Profit & Loss (PnL), Win Rate, and $R$-multiple generated by *each specific trader's manual actions*, completely separate from the automated system's PnL. This tracks human edge versus machine edge.

## 4. The Live Monitoring Dashboard UI
The central hub for the team during market hours.

*   **System Health Bar:** Real-time ping to exchanges, API limits remaining, database CPU load, and current execution slippage metrics.
*   **The Aggregated Portfolio:** A global view of total nominal exposure across all connected exchanges (Crypto + Equities), split by asset class and long/short bias.
*   **Active Strategies Feed:** A scrolling log of what the math engine is currently "thinking" (e.g., `09:30 AM: BTC passing 2X Sigma, awaiting Volatility check before entry`).
*   **Manual Intervention Interface:** A prominent section allowing an authorized Trader to manually override an active algorithmic position (e.g., clicking 'Close Position NOW - Override Algo') in the event of breaking market news that the math models cannot process.

## 5. Dynamic Routing & Contextual 404 Error Pages
The system must gracefully handle navigation errors while maintaining strict security per the user's privilege level (Admin vs. Trader vs. Analyst). This is critical for both security and user experience.

*   **Role-Based Access Control (RBAC) in Routing:** The frontend will enforce strict routing. If an Analyst tries to access `/admin/kill-switches`, the system must intercept this.
*   **Dynamic 404 Error Pages:** The "Page Not Found" (404) or "Unauthorized" (403) screens will dynamically render content based on the logged-in user's role:
    *   *Admins:* See a 404 page featuring quick links to system diagnostics, error logs, and user management.
    *   *Traders:* See a 404 page redirecting them safely back to their active portfolio view or the execution terminal, ensuring they aren't stuck during fast-moving markets.
    *   *Analysts:* See a 404 page pointing back to the research dashboards and historical data querying interfaces.
*   **Ongoing Maintenance:** The 404 page and primary navigation structures must be continuously updated as new modules are developed, ensuring users always have clear paths back to their authorized sections.
